# Принятые решения

Короткий журнал. Не пересматривать без новой причины; при пересмотре — дописать новую запись, а не стирать старую.

| # | Решение | Почему |
|---|---|---|
| 1 | Тема: обучающая платформа (атлас + тесты + аналитика), начиная с клетки | Ложится на ТЗ лабораторной, связана с НИР, есть запрос медуниверситета |
| 2 | Клиент на Angular, а не React | Требование ТЗ; Angular задаёт архитектуру (DI, сервисы), проще не смешивать UI и данные |
| 3 | 3D-ядро — отдельный проект на чистом TS, без Angular | В старом проекте react-three-fiber смешал рендер DOM и 3D; ядро переиспользуемо и тестируемо отдельно |
| 4 | three.js, а не Babylon.js | Опыт автора, наработки из атласа, всё нужное есть в экосистеме; смена движка съест время |
| 5 | Модель, манифест и контент — раздельные слои | Новые модели подключаются конфигом, без кода; основа для открытой системы и API Catalog |
| 6 | Явное сохранение состояния уровня (`ViewState`) | Без него при переходах меши «улетают», камера сбрасывается |
| 7 | Позиции расслоения всегда вычисляются из манифеста | Исключает накопление ошибок положения |
| 8 | Выбор одиночным кликом, переход двойным или повторным | На сенсорных экранах нет наведения; новичок не проваливается неожиданно на уровень ниже |
| 9 | Правая панель — только информация; настройки вида — в оверлее над холстом | Не перегружать панель; настройки нужны и при скрытой панели |
| 10 | Хлебные крошки + URL на каждый уровень | Ориентация при глубине больше двух; работает «назад» браузера и прямые ссылки |
| 11 | Мобильная версия: бургер + нижняя шторка с тремя точками остановки | Ограничение места; привычный паттерн |
| 12 | Шторка — свой компонент, а не Ionic / `MatBottomSheet` | Нужны точки остановки, жесты и связь с камерой (`setViewportInsets`) |
| 13 | Angular Material + CDK для стандартных элементов | Ближе всего к MUI, официальная поддержка, покроет будущие админские экраны |
| 14 | SCSS, токены через CSS custom properties | Темизация Material на SCSS; компоненты зависят только от токенов |
| 15 | Один детальный ЭПР с двумя частями вместо двух моделей | Биологически точнее, нет отдельной модели гладкого ЭПР |
| 16 | Сначала клиент на локальных JSON, бэкенд потом | Сроки; репозиторий за токеном DI делает подмену дешёвой |
| 17 | Бэкенд: Quiz на NestJS, одна СУБД PostgreSQL, Redis опционален, модели в MinIO | См. `docs/06-backend.md` |
| 18 | Система строится на одной модели клетки; детальные уровни сначала на заглушках, настоящие модели — по одной потом | Меньше риска «каши»; механизм переходов проверяется заранее, добавление модели не требует кода |
| 19 | Корневая модель — «Animal cell 2.0» (montanna, CC BY 4.0), подготовка скриптом, а не вручную в Blender | Воспроизводимо, со встроенными проверками; см. `docs/models/animal-cell.md` |
| 20 | Селекторы манифеста сопоставляются с исходными именами узлов glTF через `parser.associations` | `GLTFLoader` санитизирует `Object3D.name` |
| 21 | Не использовать `gltf-transform instance`; инстансинг — в ядре по `render.instanced` | `instance` стирает имена узлов |
| 22 | Режимы клика `pick: select / pass / block` вместо флага `pickable`; луч проходит по всем пересечениям | Полупрозрачные наполнители не должны перехватывать клики, а плоскость среза — должна |
| 23 | Иерархия узлов в подготовленной модели повторяет строение (Nucleus → компоненты, RoughER → мембрана + рибосомы); часть захватывает узел с поддеревом | Составной органоид на уровне родителя выделяется целиком, манифест короче и понятнее |
| 24 | Повторяющиеся органоиды — одна часть с `select: "each"` (экземпляры выбираются по одному, описание и переход общие) | Три митохондрии — три объекта, а не один; сотни рибосом не описываются поштучно |
| 25 | Центросома выбирается целиком (две центриоли), гладкий ЭПР — целиком (три сегмента) | Это одна структура из нескольких кусков |
| 26 | На уровне клетки шероховатый и гладкий ЭПР — две части с общим узлом `EndoplasmicReticulum` и одной детальной моделью (с фокусом) | В учебнике это два разных понятия; на детальном уровне видна их связь. Объединить в одну часть — одна строка манифеста |
| 27 | Удаляя объекты из модели, проверять их рендером: видимость в обычном виде **и** при подсветке/изоляции | Крупная «рибосома» сначала была сохранена как видимая заливка ядра, но при подсветке ядра оказалось, что она торчит сквозь ЭПР. Итог: удалена, цвет ядра компенсирован материалом нуклеоплазмы в скрипте |
| 28 | Постоянный кэш моделей на клиенте — Cache Storage в приложении (`ModelCacheService`), ядро получает модель через `ViewerConfig.fetchModel` | Мгновенные повторные открытия и работа без сети; ядро не зависит от хранилищ браузера; версия в пути делает кэш «навсегда» безопасным |
| 29 | Порядок после экрана атласа: сноски → расслоение → настоящая детальная модель → мобильная версия → кэш | Сначала то, что видно на демонстрации в медуниверситете; кэш почти незаметен при показе. Сноски раньше расслоения — расслоение потом проверяется сразу и на пикинге, и на подписях |
| 30 | Детальная митохондрия — «Mitochondria - Cell Organelles» (Vida Systems, CC BY-NC-ND 4.0), а не CC BY-модель CAPTAAINRO | Объекты уже разделены по смыслу (оболочка, кристы, матрикс, мтДНК, гранулы), 45 тыс. треугольников; модель CAPTAAINRO — 523 тыс. треугольников, куски без смысла, части различимы только по текстуре. ND соблюдается: в файле только технические изменения (CC 4.0, п. 2(a)(4)), разметка — в манифесте. NC: при коммерческом использовании модель заменить или получить разрешение автора |
| 31 | `select: "each"` с несколькими найденными узлами: экземпляр — каждый найденный узел | В загружаемых моделях повторы редко сгруппированы под общим узлом; поведение для одного узла (экземпляры — дети) не меняется |
| 32 | `material.alphaMode` в манифесте | В модели митохондрии у всех частей `BLEND` — непрозрачные кристы рисуются с ошибками сортировки и пропадают за оболочкой. Исправляется во время работы, без правки файла |
| 33 | Порядок подключения модели: скрипт — только для дефектов геометрии, всё остальное — манифест | Совпадает с будущей загрузкой моделей пользователями: программа должна принимать модель «как есть» и размечать её конфигом |
| 34 | Расслоение: столбец рядом с моделью + стопки по `direction` с зазорами по габаритам, а не радиальный разлёт от центра | Радиальный разлёт ставил ядро и шероховатый ЭПР в одну точку (центры обоих у центра клетки) и выносил части за кадр; у вытянутой митохондрии зазоры от радиуса модели получались неравномерными. Столбец совпадает с макетом `03-desktop-exploded.png` |
| 35 | Камера при расслоении: авто-вписывание при включении, возврат к прежней камере при выключении, если пользователь её не трогал | Иначе части улетают за кадр; ручные действия пользователя не перебиваются; состояние восстанавливается через `ViewState` |
| 36 | Опции вида делятся на опции уровня (`exploded`, `isolate`) и общие (`labels`, `hover`); источник состояния — ядро, приложение отражает его по событиям `options` / `select` | Две копии опций (сигнал стора и ядро) расходились: расслоение переносилось на детальный уровень, а при возврате сцена была расслоена при неактивной кнопке; так же терялся восстановленный выбор |
| 37 | Минимальная версия лабораторной — без Redis, k6 и пользователей; пользователь анонимен (`clientId` в `localStorage`) | Жёсткий срок; ТЗ этого не требует. Redis и k6 — потом, по плану `06-backend.md` |
| 38 | Брокер — RabbitMQ, а не Kafka | Проще в запуске; DLQ и накопление очереди при отказе потребителя — готовая демонстрация |
| 39 | Quiz ищет Catalog через Consul, а не по фиксированному адресу | Прямая связь сервисов тоже идёт через Service Discovery; работает при `--scale catalog` |
| 40 | Один origin: gateway отдаёт `/api`, `/models` (MinIO) и SPA | `model.url` в манифестах не меняется, CORS не нужен |
| 41 | Catalog хранит манифест целиком (`jsonb`) + нормализованные части; валидация — на клиенте | Формат манифеста — уже контракт (`05-manifest.md`); части в таблице нужны для запросов и связей с сущностями |
| 42 | MinIO: образ `minio/minio` закреплён на `RELEASE.2025-04-22T22-12-26Z` — последней версии с полной веб-консолью | Начиная с мая 2025 г. консоль урезана; этот тег удобен на показе. Проект архивирован в 2026 г., новых образов нет; замена без изменений кода — `pgsty/minio`, Garage, SeaweedFS |
| 43 | События публикуются после коммита, без outbox; идемпотентность — по `eventId` в Analytics | Минимальная версия; риск потери события при падении между коммитом и публикацией принят, outbox — потом |
| 44 | Сервисы регистрируют в Consul IP контейнера, `ID = name-hostname`, повторная регистрация каждые 30 с; ответы несут `X-Instance` (gateway свой не ставит) | Корректная работа `docker compose --scale`; переживает перезапуск dev-Consul; видно балансировку на защите |
| 45 | MinIO в compose: `pgsty/minio:RELEASE.2026-08-04T00-00-00Z` вместо `minio/minio:RELEASE.2025-04-22T22-12-26Z` | Исходный образ удалён с docker.io, quay.io требует авторизацию (401); `pgsty/minio` — замена из решения 42, код не меняется. Версия консоли может отличаться от описанной в 42 |
| 46 | Quiz: Prisma 7.10.1 (стабильная) и TypeScript 5.9.3, сборка `tsc` | `prisma@latest` на 17.11.2026 — 8.0.0-rc; TypeScript 7 (нативный) с Nest-инструментами не проверялся |
| 47 | Catalog работает с MinIO через AWSSDK.S3 (path-style), а не через Minio SDK | MinIO архивирован; стандартный S3 API подходит к `pgsty/minio` и аналогам без изменений кода |
| 48 | Миграции, seed и синхронизация моделей Catalog — фоновая служба; до их завершения `/health` = 503 | Consul не пускает трафик на неготовый экземпляр; процесс не падает при недоступных БД/MinIO |
| 49 | Gateway: один `IProxyConfigProvider` читает `ReverseProxy` из appsettings и подставляет адреса из Consul; первый опрос в `StartAsync` | Нет дублирования конфигурации; маршруты готовы до первого запроса |
| 50 | Gateway: повтор `GET`/`HEAD` на другом экземпляре при транспортной ошибке, пассивные проверки (окно = реактивация = 10 с), `ConnectTimeout` 2 с; при всех помеченных экземплярах запрос всё равно идёт на них | Остановка или `kill` экземпляра проходят без 502; единственный экземпляр не выключается на 10 с из-за одной ошибки |
| 51 | Тесты Quiz — Jest в ESM-режиме (`--experimental-vm-modules`, `ts-jest` `useESM`), сборка — CommonJS через `tsc` | NestJS 12 только ESM; Jest на Node 22 не загружает ESM через `require` |
| 52 | Ответ и завершение попытки сериализуются блокировкой строки попытки (`SELECT … FOR UPDATE`); `TestCompleted` — только при первом `complete` | Двойной клик, две вкладки и `--scale quiz=2` не дают дублей ответов и событий |
| 53 | Id вопросов и вариантов seed Quiz — детерминированные UUID от `quizId/номер`; порядок вариантов — стабильная перестановка | Пересев не ломает статистику Analytics; верный ответ не всегда первый |
| 54 | События Quiz публикуются без ожидания; `amqp-connection-manager` держит сообщение до 10 с до подтверждения брокера | Уточнение решения 43: ответ не зависит от брокера, короткий обрыв не теряет событие |
| 55 | `CatalogClient` Quiz при недоступном Consul использует последний известный список Catalog; `prisma` — рантайм-зависимость (`migrate deploy` в entrypoint) | Поведение как у gateway; миграции применяются при старте контейнера |
| 56 | Analytics создаёт схему `metadata.create_all` под `pg_advisory_xact_lock`, без Alembic | 3 таблицы, схема не меняется; Alembic — при первом изменении существующей таблицы |
| 57 | Потребитель Analytics: `aio_pika.connect_robust` + ретраи первого подключения; обработка отделена от AMQP (`handle(body) -> ack/reject/requeue`); ошибка БД → requeue с паузой 1 с, невалидное → DLQ | Топология восстанавливается после разрыва; обработка тестируется без брокера; нет горячего цикла при лежащей БД |
| 58 | Клиент: владелец просмотрщика `ViewerService.owner` (`'atlas' \| 'quiz'`); `ViewerHostComponent` и `LabelLayerComponent` получают данные через `input()`, не через `AtlasStore` | Один холст на атлас и тесты; двойной клик в тесте не открывает детальный уровень атласа |
| 59 | Раздел `/quiz` — оболочка с холстом и дочерними маршрутами списка и прохождения; в ядро уходят только изменившиеся опции вида | Просмотрщик не пересоздаётся; повторный `exploded: false` ядро считает выходом из расслоения |
| 60 | `HttpStructureRepository` кэширует только окончательные ответы (`200`, `404`) | «Повторить» после сбоя Catalog снова идёт в сеть |
| 61 | Этапы 1–3 лабораторной выполнялись параллельно в четырёх сессиях по сервисам (отдельные ветки), слияние и общая проверка — в `lab-backend` | Сжатые сроки; сервисы пишутся по `contracts.md` и не зависят от кода друг друга. Отчёты сессий — `docs/lab/reports/` |
| 62 | Ошибка получения манифеста — отдельное состояние `AtlasStore.dataError` (окно «Не удалось загрузить данные атласа» + «Повторить» = повторная синхронизация с URL), а не только ошибка ядра | При недоступном Catalog атлас показывал пустую сцену без сообщения |
