# Бэкенд (для лабораторной)

Не разрабатывается сейчас. Клиент пишется так, чтобы подключение бэкенда свелось к замене реализации репозитория (`docs/03-frontend-architecture.md`).

Схема согласована с преподавателем дисциплины в FigJam («Анатомическая обучающая платформа — архитектура»).

## Компоненты

| Компонент | Технология | Ответственность |
|---|---|---|
| Веб-клиент | Angular + viewer-core | UI и 3D |
| API Gateway | YARP (C#) | единая точка входа, маршрутизация, CORS, auth, rate limit |
| Service Discovery | Consul | регистрация сервисов, health checks; gateway берёт адреса из Consul (нужен небольшой провайдер конфигурации YARP) |
| Catalog Service | C# / ASP.NET Core | анатомические данные, манифесты, контент, метаданные моделей, загрузка моделей в MinIO |
| Quiz Service | TypeScript / NestJS | тесты, вопросы, попытки, итоговые результаты |
| Analytics Service | Python / FastAPI | статистика по событиям ответов, дашборды |
| Message Broker | RabbitMQ | асинхронные события |
| PostgreSQL | один сервер, отдельные БД: `catalog_db`, `quiz_db`, `analytics_db`; свой пользователь у каждого сервиса | хранение |
| Redis | опционально | кэш данных Catalog, сессии активных тестов (TTL); ключи с префиксами `catalog:*`, `quiz:*` |
| MinIO | S3-совместимое хранилище | файлы моделей `.glb`; отдача через presigned URL или gateway |

Все сервисы stateless, запускаются в нескольких экземплярах через `docker compose up --scale`.

## Взаимодействия

**Прямые (REST):**
- Клиент → Gateway → Catalog / Quiz / Analytics.
- Quiz → Catalog: данные органов и узлов для генерации вопросов.
- Клиент → MinIO (через gateway или presigned URL): файлы моделей.

**Через брокер:**
- `AtlasContentUpdated` (Catalog → Quiz): Quiz сбрасывает свой кэш данных Catalog.
- `AnswerSubmitted`, `TestCompleted` (Quiz → Analytics): Analytics копит статистику.
- (опционально) `ModelUploaded` → сервис обработки моделей (оптимизация, превью) → `ModelProcessed`.

Analytics пишет данные только из брокера, а отдаёт их по REST (`GET /api/analytics/...`).

Quiz хранит итоговые результаты попыток у себя (источник истины), Analytics — подробный поток событий и агрегаты (производные данные).

## Принятые решения

- Java заменена на TypeScript / NestJS для Quiz (опыт автора).
- MongoDB заменена на PostgreSQL для аналитики: ТЗ требует одну СУБД любого типа; JSONB закрывает гибкость схемы. При росте — колоночная СУБД (ClickHouse), замена не затронет другие сервисы благодаря брокеру.
- Redis — оптимизация, а не обязательный компонент. План для защиты: замер k6 без Redis → добавить Redis → тот же замер, графики «до/после».
- Модели — в MinIO, т. к. stateless-сервисы не могут хранить файлы на своём диске.
- Кэширование моделей на трёх уровнях: на клиенте — Cache Storage (`ModelCacheService`, см. `docs/03-frontend-architecture.md`); в HTTP — модели отдаются с `Cache-Control: public, max-age=31536000, immutable` (версия в пути, поэтому безопасно), манифесты — с коротким `max-age` / `ETag`; на сервере — Redis для данных Catalog. Для защиты: показать, что повторная загрузка модели не доходит до сервера (k6 / DevTools).

## Демонстрация для защиты

- Масштабирование: несколько экземпляров Quiz, балансировка через Consul.
- Отказ экземпляра: health check, перенаправление запросов, сессия теста не теряется (Redis / PostgreSQL).
- Отказ Analytics: события копятся в очереди, после восстановления обрабатываются.
- Нагрузочное тестирование k6, идемпотентные обработчики, dead-letter очередь.
